# Executive Summary

A full forensic audit of the **Server Monitoring System** repository was conducted, evaluating backend, frontend, agent, database, routes, authentication, authorization, WebSockets, queues, caching, telemetry, provisioning, and documentation.

The system features a sophisticated telemetry ingestion pipeline (supporting TimescaleDB hypertable rollups), an asynchronous heartbeat mechanism with dynamic offline detection, and a cryptographic agent identity model (RSA-SHA256 challenge-response and unique `installation_uuid` enforcement per ADR-0002). 

However, critical boundary defects and security vulnerabilities were discovered:
1. **Ad-Hoc Authorization Vulnerabilities (P0):** Monitored filesystem paths and global daemon settings rely on substring email checks (`str_contains($user->email, 'admin')`), allowing unauthorized users whose email contains "admin" to manipulate agent configurations and global monitoring intervals.
2. **Unauthenticated Infrastructure Reconnaissance (P0):** `GET /api/v1/servers/{server:uuid}/report` is declared outside authentication middleware, exposing internal hardware specs, OS details, client names, and activity logs to the unauthenticated public internet.
3. **Session Rotation Race Conditions (P1):** Multi-tab access token refreshes cause concurrent requests with the pre-rotation token, triggering false-positive reuse detection that immediately revokes and compromises legitimate user sessions.
4. **WebSocket Cross-Client Isolation Bypasses (P1):** Private Reverb channels (`server.{uuid}`, `agent.{uuid}`, `system-telemetry`) authorize all authenticated users unconditionally without verifying client or server ownership.
5. **Broken API Endpoints (P1):** Legacy telemetry routes (`/server/{id}/minute` and `/server/{id}/{date}`) map to non-existent methods on `ServerController`, causing unhandled HTTP 500 crashes.
6. **Multi-Server Agent Collateral Decommissioning (P2):** Clearing an offline server from the dashboard revokes the host's singleton `Agent` record and decommissions all sibling servers monitored by that agent.

Total Findings: **12** (2 Critical, 4 High, 4 Medium, 2 Low).

# Mental Model

### 1. Identity & System Identifiers
- **User Identity:** `users.id` (bigint auto-increment) + `users.uuid` (UUIDv4). Users authenticate via email/username + bcrypt password.
- **User Session:** `user_sessions.session_uuid` (UUIDv4). Tracks single device/browser sessions with paired JWT access tokens (HMAC-SHA256, 15m TTL) and refresh tokens (ULID + 256-bit entropy, 30d TTL).
- **Client Identity:** `clients.id` + `clients.uuid` (UUIDv4). Multi-tenant organizational unit owning servers.
- **Server Identity:** `servers.id` (bigint internal PK) + `servers.uuid` (UUIDv4 external routing parameter).
- **Agent Identity:** `agents.id` (bigint PK) + `agents.installation_uuid` (UUIDv4 unique per physical machine, immutable). Each agent holds a local RSA-2048/4096 keypair and registers its public key and SHA-256 fingerprint with the backend.
- **Cross-System Cardinality:** Per ADR-0002, 1 physical installation = 1 `Agent` record (`installation_uuid` unique) ──* N `Server` records (via `servers.agent_id`).

### 2. Ownership & Authorization Model
- The application dropped its legacy database role table (`2026_06_29_000001_remove_roles.php`).
- Access control relies on:
  1. `secopclients` pivot table assigning SecOps users to specific clients.
  2. Route prefixing: `/clients/{clientUuid}/servers/...` verifies SecOps client membership.
  3. Ad-hoc admin checks: String comparisons against `'admin'`, `'admin@example.com'`, or substring matching.

### 3. Agent Lifecycle & Cryptographic Authentication
```text
[ Provisioning ]
  Dashboard Admin -> POST /servers/{uuid}/provision -> Generates single-use ProvisionToken (1h TTL)
  Admin executes curl/powershell installer on host machine with raw token & installation_uuid

[ Registration & Key Exchange ]
  Agent generates local RSA keypair (NCrypt Windows Keystore / Linux 0600 file)
  Agent -> POST /api/v1/provision (validates token, downloads binary matching sha256)
  Agent -> POST /api/v1/register (sends installation_uuid + public_key + public_key_hash)
  Backend sets server to 'waiting_for_first_heartbeat', binds server to Agent record

[ Challenge-Response Authentication ]
  Agent -> POST /api/v1/agent/auth/challenge (sends public_key_hash)
  Backend returns random challenge string (60s TTL stored in cache/database)
  Agent signs challenge with local private key (RSA-SHA256)
  Agent -> POST /api/v1/agent/auth/verify (sends signed challenge)
  Backend verifies signature using registered public key -> Issues 24h signed agent session token

[ Heartbeat & Telemetry Ingestion ]
  Agent ticks every 5 seconds (configurable)
  Agent -> POST /api/v1/agent/heartbeat (Bearer agent token)
  Payload: CPU, RAM, Disks, Network, Services, Ports, Processes, Completed Commands
  Backend ingests metrics into TimescaleDB hypertable -> Emits SystemTelemetryEvent -> Emits ServerStatusUpdated
```

### 4. Security Boundary Map
1. **Public Internet Boundary:** `routes/api/v1/auth.php` (login, refresh, forgot-password, reset-password) and `routes/api/v1/agent.php` (provision, register, challenge, verify, heartbeat).
2. **Authenticated Operator Boundary:** Protected by `auth:jwt` guard. Verifies access token HMAC signature, expiration, and user existence.
3. **Tenant/Client Isolation Boundary:** SecOps users must only access servers and audit streams belonging to their assigned clients.
4. **Agent Control Boundary:** Signed agent session tokens authorizing telemetry reporting and command completion.
5. **Real-Time WebSocket Boundary (Laravel Reverb):** Private channels (`private-server.{uuid}`, `private-agent.{uuid}`, `private-dashboard`).

# Verified Invariants

1. **Unique Agent Installation per Host:** The database table `agents` enforces `UNIQUE(installation_uuid)`. Re-installing or registering an existing agent updates the existing installation rather than duplicating agent daemons.
2. **One-Time Provisioning Tokens:** `ProvisionToken` transitions to `status = 'used'` inside a database transaction during registration, preventing replay attacks.
3. **Cryptographic Agent Challenges:** Agent challenges are single-use, enforce a 60-second time-to-live, and require RSA-SHA256 signature verification matching the registered public key.
4. **Decommissioned Server Guard:** `HeartbeatService` and `AgentController` reject heartbeats for servers where `agent_deleted = true` or `status = 'archived'`, refusing to resurrect decommissioned instances.
5. **Session Expiry Enforcement:** `SessionManager` and `UserSession` calculate expiration based on `last_activity_at + 30 days` and verify `revoked_at === null` during refresh rotation.

## [x] AUDIT-001 — Insecure Authorization Check in `WatchedPathController` and `SettingController` Removed [FIXED]
**Severity:** P0  
**Confidence:** HIGH  
**Status:** Approved for Implementation — FIXED

### Claim
Administrative authorization in `WatchedPathController::ensureAdmin()` and `SettingController::update()` relies on a naive substring check (`str_contains($user->email, 'admin')`), granting full administrative write privileges to any user whose email address contains the word "admin".

### Observation
In both controllers, the method intended to restrict access to system administrators evaluates:
```php
$isAdmin = $user && ($user->username === 'admin'
    || $user->email === 'admin@example.com'
    || str_contains((string) $user->email, 'admin'));
```
Any user account with an email like `badminguy@gmail.com`, `admin-assistant@client.org`, or `leadmind@company.com` evaluates `$isAdmin` as `true`.

### Evidence
#### File
`app/Http/Controllers/Api/V1/WatchedPathController.php`
#### Symbol
`WatchedPathController::ensureAdmin()`
#### Location
Lines 20–28:
```php
private function ensureAdmin(Request $request): ?JsonResponse
{
    $user = $request->user();
    $isAdmin = $user && ($user->username === 'admin'
        || $user->email === 'admin@example.com'
        || str_contains((string) $user->email, 'admin'));

    return $isAdmin ? null : response()->json(['message' => 'Forbidden.'], 403);
}
```

#### File
`app/Http/Controllers/Api/V1/SettingController.php`
#### Symbol
`SettingController::update()`
#### Location
Lines 32–36:
```php
public function update(): JsonResponse
{
    $user = request()->user();
    $isAdmin = $user && ($user->username === 'admin' || $user->email === 'admin@example.com' || str_contains($user->email, 'admin'));
    if (! $isAdmin) {
        return response()->json(['message' => 'Forbidden.'], 403);
    }
```

### Execution Path
```text
Attacker (creates or logs into account with email containing "admin", e.g. "guest_admin@domain.com")
→ Sends POST /api/v1/watched-paths OR PUT /api/v1/settings
→ JwtAuthenticate passes (valid JWT token)
→ WatchedPathController::store() / SettingController::update()
→ ensureAdmin() executes: str_contains("guest_admin@domain.com", "admin") returns true
→ Full write access granted to system-wide settings and watched file audit configurations
→ AgentConfigUpdated broadcast to all active agents in the system
```

### Expected Invariant
Administrative actions must be gated by verified permissions, an explicit role/attribute column on the `users` table, or a strictly defined whitelist in configuration (`config('auth.admin_usernames')`), never by substring patterns on user-supplied email strings.

### Reasoning
- **Observation:** Both controllers inspect the email string for substring occurrence of `"admin"`.
- **Evidence:** `str_contains((string) $user->email, 'admin')` in both files.
- **Invariant:** Only verified system administrators should modify monitored filesystem paths and global daemon settings.
- **Conflict:** Any normal SecOps user whose personal or corporate email includes `"admin"` accidentally or maliciously acquires unrestricted root-level monitoring control.
- **Execution Path:** User registers or changes email to contain "admin" -> logs in -> calls protected endpoints -> gains admin privileges.
- **Impact:** Privilege escalation across all monitored systems, watched file paths, and global daemon intervals.
- **Counter-Check:** Searched for route-level or gate-level filters. The routes are wrapped only in `Route::middleware('auth:jwt')`. There are no Laravel Policies or middleware intercepting these calls.
- **Conclusion:** Confirmed critical authorization vulnerability.

### Reproduction / Failure Scenario
1. Initial state: User account created with email `robert.radmin@secops.local`.
2. Action A: User logs in, receives valid JWT.
3. Action B: User sends `PUT /api/v1/settings` with `{"heartbeat_interval": 60, "offline_threshold": 120}`.
4. Result: Server returns HTTP 200 and updates global settings for all servers.
5. Expected: HTTP 403 Forbidden.

### Affected Components
- `WatchedPathController`
- `SettingController`
- WebSocket config broadcast dispatcher

### Related Findings
- AUDIT-004

### Recommended Direction
Replace the substring match with an explicit, strict check against a configured whitelist (e.g. `in_array($user->username, config('auth.admin_usernames', ['admin']), true)`) or introduce an explicit boolean `is_admin` flag on the `users` table.

### Why This Matters
Allows arbitrary authenticated users matching an email pattern to perform destructive administrative operations and alter system configurations.

### Confidence Reasoning
HIGH — Directly verified from source code and routing definitions.

### Human Decision
- [x] Approve
- [ ] Reject
- [ ] Needs more verification
- [ ] Defer

### Human Notes
Approved with directive: "there is no role so remove admin, change the seeded name as 'user' instead of admin to prevent confusion".

### Fix Implementation & Verification
- Removed `ensureAdmin` from `WatchedPathController` and removed `$isAdmin` gating from `SettingController`.
- Updated seeders (`AdminSeeder`, `DatabaseSeeder`, `ClientSeeder`, `load-test-factory.php`) to seed user `'user'` (`user@example.com`, name 'User').

## [x] AUDIT-003 — Refresh Token Rotation Concurrency Grace Window Added [FIXED]
**Severity:** P1  
**Confidence:** HIGH  
**Status:** Approved for Implementation — FIXED

### Claim
When an application with multiple tabs issues simultaneous refresh requests, `RefreshTokenRotationService` interprets the concurrent use of the pre-rotation token as a malicious reuse attack, immediately and permanently marking the user's session as compromised and revoking access.

### Observation
When Tab A and Tab B simultaneously detect an expired access token, both submit `POST /api/v1/refresh` with the same cookie. Tab A arrives first, rotates the token in `SessionManager::rotateRefreshToken`, and stores the previous token ID in `previous_refresh_token_id`. When Tab B arrives milliseconds later, `findSessionByRefreshTokenId` returns `null`, but `findSessionByPreviousRefreshTokenId` returns the session. This immediately invokes `handleReuseDetection()`, executing `$session->compromise(...)` and invalidating the entire user session.

### Evidence
#### File
`app/Services/RefreshTokenRotationService.php`
#### Symbol
`RefreshTokenRotationService::validateAndRotate()`
#### Location
Lines 25–37:
```php
$session = $this->sessionManager->findSessionByRefreshTokenId($tokenId);

if (! $session) {
    $session = $this->sessionManager->findSessionByPreviousRefreshTokenId($tokenId);

    if ($session) {
        $this->handleReuseDetection($session, $ip, $userAgent);

        return ['error' => true, 'message' => 'Refresh token reuse detected. Session compromised.', 'status' => 401];
    }

    return ['error' => true, 'message' => 'Invalid refresh token', 'status' => 401];
}
```

### Execution Path
```text
Browser Tab A (Token T1)                 Browser Tab B (Token T1)
       │                                        │
       ├─► POST /api/v1/refresh ────────────────┼─► POST /api/v1/refresh
       │   (finds session by T1)                │   (in flight...)
       │   Rotates: current=T2, prev=T1         │
       │   Returns 200 (cookie=T2)              │
       │                                        ▼
       │                            Arrives at RefreshTokenRotationService
       │                            findSessionByRefreshTokenId(T1) -> null
       │                            findSessionByPreviousRefreshTokenId(T1) -> $session
       │                            Calls handleReuseDetection()!
       │                            $session->compromise() -> revoked_at = now()
       ▼                                        ▼
User abruptly logged out in both tabs with "Session compromised"
```

### Expected Invariant
Benign concurrent network calls from the same client session during access token expiration should either coalesce or provide a short grace window (e.g. 10–30 seconds) allowing the immediate predecessor token without triggering malicious compromise lockout.

### Reasoning
- **Observation:** `validateAndRotate` has no grace window, lock, or mutex for in-flight requests.
- **Evidence:** Lines 27–34 of `RefreshTokenRotationService.php`.
- **Invariant:** Normal browser usage across multiple tabs must not result in session termination.
- **Conflict:** Two tabs triggering refresh simultaneously causes one tab to trigger reuse detection.
- **Execution Path:** Rapid concurrent refreshes from multiple tabs or concurrent background API calls -> second request matches previous token -> triggers immediate compromise.
- **Impact:** Random, frustrating user logouts and false-positive security audit alerts.
- **Counter-Check:** Inspected `SessionManager::rotateRefreshToken` and frontend axios interceptor. The backend does not lock on the session ID. While frontend has a single-tab request queue, multiple tabs operate with independent JavaScript runtimes and cookies, sending parallel requests.
- **Conclusion:** Confirmed high-severity concurrency flaw in authentication lifecycle.

### Reproduction / Failure Scenario
1. Open dashboard in Tab 1 and Tab 2.
2. Wait 15 minutes for access token expiration (or manually invalidate access token in memory).
3. Simultaneously navigate or trigger an action in both tabs.
4. Both tabs send `POST /api/v1/refresh`.
5. Result: One tab succeeds, the other receives 401 "Refresh token reuse detected. Session compromised." Both tabs are immediately logged out.

### Affected Components
- `RefreshTokenRotationService`
- `SessionManager`
- Frontend API client interceptors

### Related Findings
- AUDIT-007

### Recommended Direction
Implement a concurrency lock (e.g. `Cache::lock('session_refresh:' . $session->id, 5)`) or permit a 10–15 second grace period on `previous_refresh_token_id` before treating it as an adversarial replay.

### Why This Matters
Causes unpredictable session termination and degraded user experience in normal production multi-tab browsing.

### Confidence Reasoning
HIGH — The code path has zero concurrency protection and unconditionally compromises the session upon predecessor token match.

### Human Decision
- [x] Approve
- [ ] Reject
- [ ] Needs more verification
- [ ] Defer

### Human Notes
Approved for implementation.

### Fix Implementation & Verification
- Added a 30-second concurrency grace window in `RefreshTokenRotationService::validateAndRotate()`: if a previous refresh token arrives within 30 seconds of rotation and the token secret matches the recorded previous hash, the service returns the active session rather than flagging reuse compromise.
- Verified in `tests/Feature/AuthTest.php` with dedicated concurrency grace period test.

# Architectural Root Causes

3. **Singleton Agent (ADR-0002) Incomplete Migration:** The shift from a 1:1 agent-to-server model to a 1:N singleton model was implemented in the agent daemon and registration, but administrative management endpoints (like dashboard `deregister`) still assume an agent belongs exclusively to one server.
